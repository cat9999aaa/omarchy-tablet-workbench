# Omarchy 平板增强系统总体方案

日期：2026年10月17日。目标设备：Dell Latitude 7220 Rugged Extreme，Omarchy / Arch Linux。用户已要求把此前讨论的方案收录为启明开发原则；本文件是整合后的书面架构，后续各阶段分别形成实施计划与验收记录。本文描述的统一架构尚未整体实现。

## 目标与范围

将已经建立的输入法、网络、电池、下拉控制台、硬件工具和工作台整合为可持续维护的平板增强系统。用户无需实体键盘，也无需记住多个脚本或处理重复的控制器。保持现有能用的开机解密、锁屏、P1/P2/P3、4G代理和ZeroTier。

首个设备配置只覆盖已验的7220硬件能力。界面适配横竖屏，也能在桌面尺寸下使用；其他型号先做能力检测与独立验收，不能直接套用7220设备命令。远程电脑仅承担用户授权的构建任务，不扩展为通用远程管理权限。

## 选择的路线

| 路线 | 代价与适用性 | 结论 |
| --- | --- | --- |
| 继续增加相互独立的脚本和面板 | 短期快，但状态、布局和权限会继续分散 | 仅保留作为迁移来源 |
| 一个产品和源码仓库，模块逐步整合 | 复用已验实现，统一界面与接口，模块可独立恢复 | 采用 |
| 全量重写桌面或制作新发行版 | 将已工作的网络、解锁和输入链路重新置于风险中，维护面过大 | 不纳入本项目 |

保持项目名 `Omarchy Tablet Workbench`。应用和模块可以分别发布，源码仍集中在一个仓库；会员代表维护责任，不对应一套独立仓库或一套界面。

## 技术栈与开发原则

| 部位 | 默认选择 | 使用边界 |
| --- | --- | --- |
| 桌面界面与交互组件 | Qt Quick / QML，沿Omarchy现有插件机制 | 共用组件、主题变量和交互状态；不另起一个网页运行时承载基础快捷面板 |
| 新增常驻逻辑与状态适配器 | Rust优先 | 按事件订阅，先证明需要新增服务；通过D-Bus等版本化接口与界面交互 |
| 已有Fcitx、Rime、Qt桥 | 保留C++ | 已通过测试的桥接代码逐步整理，不为统一语言全量重写 |
| 独立构建或网络工具 | Go可选 | 现有能力不能合适复用、且收益明确时使用；不同时维护重复控制器 |
| 底层接口、上游集成 | C或上游原语言 | 以兼容性和可验证性决定 |
| 汇编 | 仅经过测量的热点 | 有基准、跨架构回退与维护必要性后再引入 |
| 安装、诊断、迁移与非高频任务 | Shell / Python可保留 | 不因语言偏好重写成熟工具；高频轮询需先测量开销 |

没有哪种语言自动保证省电。依赖复用、事件驱动、合理刷新频率、避免重复进程与远程编译优先于语言迁移。

所有修改继续遵循Omarchy官方 → Arch官方 → 厂商Linux上游 → 社区。使用用户配置和扩展接口，不改打包的Omarchy源文件。先备份、再验证、再版本化启用；修改网络和启动链路必须保留可用恢复路径。

## 统一界面

共享一套EVA机甲控制台风格：深石墨底色、紫色主色、荧光绿强调、琥珀提示、红色故障。主题通过语义变量表达；文字、图标、按钮、卡片、页签和状态标记使用同一套组件。官方主题是适配基础，EVA作为项目主题包；正式应用前单独完成横竖屏设计和可读性验证。

- 中文正文字体优先清晰、覆盖完整；等宽字体只用于数字、代码和诊断值。
- SVG图标使用统一网格、线宽与状态语义，绘制原创素材；警告与成功不能只靠颜色区分。
- 常用触屏目标至少48个逻辑像素，主要按钮以56为起点；实际尺寸依设备缩放和手指试用校准。
- 面板可随屏幕方向改变布局，切换页签保持当前外框稳定。长内容在内部滚动，缺少数据保留状态占位。
- 固定页头显示当前全局状态；每页显示本模块连接状态、最近更新时间与错误。操作期间显示进行中，失败时显示可执行的重试入口。
- 常用操作靠近下方手指区域；候选贴近键区，禁止大块空白隔断输入与选字。
- 动画只用于打开、关闭、切页和操作反馈，尊重系统减少动画设置；隐藏界面停止绘制，避免持续闪烁或后台装饰动画。
- P1仅手动呼出唯一桌面输入法；P2保持语音入口；P3保持既有系统授权边界；旋转实体键保持应用操作菜单。不恢复用户否定的额外标题栏。

## 模块与状态控制

| 模块 | 责任与入口 | 依赖及边界 |
| --- | --- | --- |
| 随身控制台 | 三指下滑、底栏备用入口、概览及快捷动作 | 聚合模块状态，不复制网络/电源执行器 |
| 中文输入与语音 | 九键/英文/符号/剪贴板/手写/听写，P1/P2 | 复用Fcitx/Rime及现有语音链路；只维护一套桌面输入法 |
| 网络中心 | Wi-Fi、有线、4G、代理、ZeroTier、GPS分页 | NetworkManager/ModemManager及现有TUN适配器；单实例、统一控制入口 |
| 电池与电源 | 双电池、充放电记录、工作模式、后台任务保护 | UPower/内核/现有电源服务；缺失读数显示未知，不编造循环次数 |
| 硬件与桌面操作 | 手套模式、笔、显示方向、窗口菜单、传感器诊断 | 7220设备配置、Hyprland及官方接口；能力未验不开放写入动作 |
| 解锁与认证 | 冷启动触屏解密、锁屏键盘、P3 | 独立安全边界和版本，密码回退保留；不并入普通桌面输入进程 |
| 开发与AI工作台 | 任务、构建、模型入口、版本和诊断结果 | 复用DeepSeek官方界面与可用扩展；基础操作无需AI或网络才能工作 |
| 娱乐与应用入口 | 游戏、影音、阅读、手机互联入口 | 维护已安装应用配置和插件，不重写播放器或游戏引擎 |

新增状态接口统一包含：版本、能力是否可用、观察到的状态、数据时间、来源、错误与待执行动作。每个动作包含请求ID，反馈“排队/执行中/成功/失败/超时”。用户点击后的期望状态与实际读回状态分别保存，不能把提交成功当作设备已完成。

网络、电源、触摸模式各有唯一控制归属。界面、CLI和工作台经过同一入口；同类动作串行处理或合并，系统事件再更新状态。权限操作使用最小白名单和Polkit等原生机制，普通界面不长期以root运行。认证完成后重新核对会话和目标，防止锁屏或设备变化后的过期操作。

先为现有后端补接口，再决定哪些适配器值得迁入Rust。输入、锁屏、启动等不同信任边界保持进程隔离，不为了“统一”变成一个大进程。

## 源码和启明归属

目前本机 `tools/` 内多个原型仍是运行与维护权威，GitHub `modules/` 部分是脱敏快照。迁移按模块进行：确认源目录 → 远程构建 → 本机回归 → 版本化部署 → 更新权威路径。完成前不同时修改两份源码，不突然移动运行服务依赖的路径。

目标仓库结构按实际迁移形成，不预建空目录：共享UI、模块源码、设备配置、打包、文档与测试。运行数据、个人词库、电池数据库、代理节点、录音、凭据和私有启明档案留在本机。

启明保留已有会员ID、父子关系与历史；用功能域索引统一展示，不批量重建会员。独立维护的工具和服务继续入会，内部组件归现有会员。每项变更记录来源任务、权威源码、部署版本、实际测试、待验项、恢复方式和GitHub范围。

## 远程构建与发布

采用已验证的专用SSH密钥、构建目录与tmux连接。重编译、打包和批量软件测试优先远程，平板运行实机验收。远程不可用时保留任务并报告，不自动让平板满载。

远程依赖优先通过Arch干净构建环境隔离；对齐Qt、Fcitx、glibc及目标架构，不使用构建机的`-march=native`。按源码版本保存产物、依赖清单、日志和校验值，回传后再安装。每次安装保留上一个可用版本。

连接、tmux及产物回传已验证。阶段1进一步完成现有Qt/C++/Rime输入法完整远程构建，9项CTest、12项边界测试、回传与平板4项隔离兼容通过；有手动prepare/submit/status/fetch入口。Rust构建、自动队列、重启恢复和统一发布器仍待实现。详情见[远程构建原则](../../design/2026-10-17-remote-build-policy.md)。

## 电源与AI

先完成本地确定性规则与测量，再评估模型。熄屏、锁屏和睡眠是三种不同状态；有后台任务时允许熄屏，但不能用自动睡眠冻结任务。用户手动电源选择优先；不叠加相互冲突的电源管理器，不盲目启用USB/蜂窝自动挂起。

Jev可作为低频的策略建议来源。其API、延迟与收益尚未实测，当前不作为电源管理依赖。模型返回的动作必须落在本地允许集合，断网或失败立即退回本地规则；API开销和计算能耗也应计入收益评估。电池底层读数跳变问题先排查，不能用模型掩盖。

## 内核与驱动优化

内核优化纳入维护范围，目标是改善本机触屏响应、调度延迟、驱动兼容、网络恢复和实际功耗。Omarchy基于Linux与Arch，先确认当前内核、配置、固件和具体瓶颈，不把更换内核本身视为性能提升。

先使用现有官方内核、受支持参数和上游修复；确有证据需要其他内核或补丁时，再制作可独立选择的试验包。编译在授权远程环境内进行，不覆盖原可启动内核。引导镜像、触屏解密与恢复入口必须一起核对，保留实体输入或其他既有可用恢复方式，重启另按具体测试安排。

每轮只改变一个因素，对比任务耗时、输入响应、温度和电池能耗；区分接电、放电与熄屏状态。调度、CPU频率、USB自动挂起、蜂窝节能不能一次性批量改变。验收覆盖冷启动解密、锁屏触屏、笔、4G/TUN、ZeroTier与睡眠恢复；未覆盖项明确保留未验。当前阶段仅确定流程，没有修改内核参数或切换内核。

## 开源与持续演化

项目转为公开开源，原创贡献采用GPL-3.0-only，第三方许可分别保留。发布前检查当前内容、所有远端分支历史、图片、Issue、运行日志与附件；私人管理档案、凭据和运行数据仍留本机。公开项目不等于公开整台设备。

启明Skill及本项目管理工具也可持续优化：发现重复工作、接续困难或状态矛盾时，改进规则或工具，保留历史并验证。具体产品模块按阶段填充；一次运行环境变更应能独立验证与恢复。

## 分阶段交付与验收

| 阶段 | 具体产物 | 完成条件 |
| --- | --- | --- |
| 0 盘点与规则 | 会员/任务清单、总体方案、源码归属表 | 已有成果与待验项明确，旧摘要不再引导重复工作；本轮完成文档盘点 |
| 1 构建基线 | 远程构建一个完整现有模块，优先输入法 | 固定源码与依赖、完整测试、产物回传与平板兼容检查、可恢复；不能只凭Hello程序 |
| 2 统一UI与状态 | 共享组件先落到控制台/网络/电池 | 页签不跳尺寸、信息不矛盾、无重复控制进程；横竖屏、实体触屏和失败状态逐项通过 |
| 3 日常体验收尾 | 输入法、三指手势、地图、互联和电池待验项 | 真实输入及复制粘贴、手势、GPS地图链路、断线恢复与电池自然周期证据 |
| 4 版本化整合 | 分模块权威源码迁移和安装恢复 | 一个模块只维护一份源码，升级/恢复通过，私有数据不被覆盖 |
| 5 AI与扩展 | 官方工作台真实任务、语音对话、电源建议 | 基础能力离线仍可用；对话延迟和电源收益可测量；无证明收益的常驻功能不启用 |

各阶段形成独立实施计划，先解决使用与稳定性问题，再扩大功能。可以在不同模块准备研究材料，但同时只推进一个影响运行环境的整合变更。

首个正式发布门槛：保留无实体键盘启动和解锁能力，只有一套桌面输入法，4G代理和ZeroTier回归通过，面板不跳尺寸、按钮读回状态一致，远程可重复构建，旧版本可恢复。已有风险记录不能被“统一完成”状态抹掉。

## 官方依据

- [Qt QML与C++集成](https://doc.qt.io/qt-6/qtqml-cppintegration-overview.html)：支持界面与逻辑分离，继续保留现有桥接层。
- [Arch makechrootpkg](https://man.archlinux.org/man/extra/devtools/makechrootpkg.1.en)：在独立chroot中构建软件包。
- [TypeSafe Jev](https://docs.typesafe.ai/introduction/quickstart)：Choice、Score、Noul是结构化判断能力，是否适合本机节能需实测。
- Omarchy扩展方式以设备上已安装版本的官方命令与源码为准，升级后重新核对接口。
