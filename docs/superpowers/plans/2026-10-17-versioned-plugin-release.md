# 版本化插件发布与恢复 · 第一批

状态：实现、独立审查修复、远程20项及本机只读检查通过，CI接入中；沿已批准总体架构阶段4；仅现有Omarchy用户插件更新，不覆盖系统包或迁移私人数据。

## 问题与范围

实际输入法0.2.3发布时，直接向被监视的插件目录逐个复制文件触发重复热加载，第一次enable与扫描竞争而失败。原manifest恢复后0.2.2正常；完整文件就绪后一次切换manifest并官方rescan，0.2.3成功。应把这一顺序固化，不继续依赖每轮临时脚本。

低频Python工具，源码先归tools/plugin-release，GitHub保存脱敏副本。它只处理已安装插件的版本化QML/JS/assets包；本轮不安装root服务、代理核心、启动文件，不迁移运行源码权威，不改个人词库。

## 接口和边界

- 输入为显式bundle目录：manifest.json（基于原官方manifest的完整候选）、files目录和sha256清单。入口全部为安全相对路径；拒绝链接、目录穿越、重复、文件缺失和内容变化。
- CLI只面向当前用户既有插件目录；ID必须与当前manifest一致，不接受任意系统目标。首次安装仍走Omarchy官方工具。
- 新版本必须不同于当前版本。固定支持四个已有只读运行探针：输入法version/ready、网络travelVersion、控制台state.version、电池workbenchState.version。不得从bundle指定任意执行命令。
- 在插件监视目录外创建完整候选并使用官方validate；准备完成后原子移入插件的独立release目录，再原子替换manifest，最后官方rescan。保持已启用配置，不反复disable/enable，不改整份shell配置。
- 操作前记录原manifest内容、hash、候选hash、版本、路径、时间；每插件加锁。替换前重核原hash，拒绝并发修改。事务备份只属于工具自身路径，不存凭据。
- 等待运行探针确认新版本并就绪才记applied。失败时只有当前manifest仍等于本次候选才恢复原件并核对旧版本；用户并发修改时保留证据、拒绝覆盖。
- 显式rollback只接受本工具已有事务，核对当前hash/插件身份/备份hash；恢复manifest，不删除旧版本或私人数据。不能把文件恢复等同运行恢复。
- dry-run只检查包与当前匹配、打印拟替换对象，不改桌面或服务。

## 测试先行与验收

1. 在临时目录和注入命令Runner中先写失败测试：包缺失/篡改/路径穿越/链接、错误ID、同版本、原manifest变化、校验失败、探针失败自动恢复、恢复探针失败、并发修改拒绝覆盖、手动恢复、保留旧release、不得调用网络/锁屏动作。
2. 实现准备/切换/恢复，所有调用固定argv而非shell文本。
3. 在授权远程构建区执行测试；接入统一软件CI。实际机先dry-run已验输入法bundle验证包和现有版本，后续新版本发布时才启用写入路径；此阶段不为测试制造额外版本或切断网络。
4. 独立审查重要项一次修复，验证通过后登记会员、任务、源码归属和恢复边界，公开代码与CI。不宣称自动发布器已完成真实升级/恢复，直到实际使用。

## Review Focus

是否可能覆盖其他插件/配置；是否能逃出源/目标目录；是否误接纳不完整包；并发修改是否被覆盖；失败是否真正恢复并读回；在watch目录外准备是否成立；运行探针是否只读；旧数据是否保留。

## Ruling

批准架构明确要求版本化整合与恢复，且本轮已有实际热加载失败证据；采用现有Python低频流程和Omarchy官方validate/rescan，无需引入新服务或再向用户索取重复授权。第一批提供工具与隔离验证，真实生产自动发布留待下一次有实际功能变化的版本使用，避免仅为测试扰动当前已验版本。
